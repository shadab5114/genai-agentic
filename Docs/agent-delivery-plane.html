Agent Delivery Plane

A harness that turns a developer instruction into a reviewed, merged pull request — and keeps going after a human leaves comments on it.

The constraint

Start here, or the rest doesn't hold

An agent's autonomy ceiling is set by the quality of the verification signal in its environment — not by the model.

If the agent can run your accessibility audit, it can fix accessibility defects unsupervised. If “correct” exists only in a senior engineer's head, no model closes that gap. So the first tranche of work is not AI work: it is making repos agent-runnable — one-command bootstrap, hermetic tests, targeted test selection, and machine-readable output from every linter, scanner, and snapshot differ you own.

Everything below assumes that groundwork. The four figures are the system: what the parts are, how a task moves through them over days, what stands between the agent and a human, and what occupies the context window while it works.

Figure 1 · System map

Two planes and one boundary

The control plane is trusted and long-lived: it holds task state, policy, and money. The execution plane is disposable and assumed hostile — it runs model-authored code against a real toolchain. Nothing crosses the boundary except a scoped task in, and events out.

Figure 2 · State machine

The task outlives the process

This is the difference between a demo and a system. A chat-style agent loop lives inside one process; a real task waits on a human for three days, across deploys, restarts, and a context window that no longer exists. So the lifecycle is an explicit finite state machine with each transition committed to a database — Temporal if you want durable execution for free, Postgres plus a queue if you'd rather own it.

Figure 3 · Gate ladder

Nothing reaches a human until it's green

The gate ladder is your Definition of Done made executable. Four of the five rungs are identical across every task type — they're just your existing CI, run early and locally. The fourth rung is the one you design per recipe, and it is the entire reason a given task can be delegated at all.

The oracle is the product decision

Pick your first recipes by how good an oracle you can write for them, not by how much time they'd save. Three that map onto the requests you already get:

RecipeTriggerWrite accessRung 4 — the oracleLaunch autonomy
mr-review@v1 MR opened, or agent:review none Offline: agreement rate against what human reviewers actually flagged on sampled MRs suggest-only
component-a11y-prep@v3 Jira label agent:a11y-prep branch, component path only XCUITest a11y audit + VoiceOver label coverage + Dynamic Type snapshot diff at M/XXL/AX5 plan-approval
intake-fix@v2 Jira label agent:fix branch, allowlisted paths A failing repro test written first and reviewed as part of the plan, then turned green plan-approval

Ship mr-review first. It is read-only so its blast radius is zero, it earns the team's trust before you ask them to accept agent-authored diffs, and every reviewer reaction to it becomes labelled data for the two recipes that follow.

Figure 4 · Context budget

What's in the window, and what it costs

Order the context window stable-to-volatile so a cache prefix can actually form, and pull specifics in through tool calls rather than pre-stuffing them. Two mechanisms do the rest of the work: sub-agents that fan out to search and return conclusions instead of file dumps, and compaction that checkpoints a long run into a structured handoff note — the same note the state machine needs to resume after review.

Measure the right number

Track cost per merged PR, never cost per token. A $12 run that merges on the first review round is worth far more than a $2 run that gets abandoned, and optimising the token number directly will push you toward the second.

Worked example

“Get the iOS Accordion ready for accessibility review”

One request traced through every box above. This is the shape of a run you should be able to read end-to-end in the trajectory viewer.

  1. TRIGGER Jira automation fires on DS-4127

    The ticket carries the label agent:a11y-prep. Jira posts to /intake. No human has typed a prompt.

  2. INTAKE Normalize, or bounce

    Resolves the ticket, matches recipe component-a11y-prep@v3, maps “Accordion” to Sources/PDS/Components/Accordion/, sets risk tier R2. The quality gate checks the ticket names a component and a target conformance level — if it doesn't, the task goes to CLARIFY and asks in the ticket rather than guessing.

  3. POLICY Budget and tool ACL are bound now

    400k tokens, 45 minutes, $8, 5 gate retries. Allowed: read the repo, edit under the component and its test directory, run xcodebuild, run the a11y audit, read the Figma node, comment on Jira. Denied: Package.swift, network egress, merge.

  4. PLAN Read first, propose second

    In a fresh ios-16.4 container the agent reads the component, the a11y playbook, the design contract, and the two most recently merged a11y PRs. It proposes: accessibility labels and values on the header control, expanded/collapsed exposed as traits, a hint on the disclosure affordance, Dynamic Type wiring, and six new audit assertions.

  5. HUMAN GATE — TIER R2 Plan posted to the ticket for approval

    Cheap to review, cheap to redirect. Catching a wrong plan here costs one comment; catching it at PR costs a review round. This gate disappears once the recipe earns tier 2 autonomy.

  6. IMPLEMENT ⇄ VERIFY Climb the ladder, twice

    Edits, then build → static → unit → oracle → diff policy. The Dynamic Type snapshot fails at AX5 on the first pass; the agent reads the diff image path and the failing size from the gate output, fixes the layout, and re-runs. Two of five retries spent.

  7. PR_OPEN A PR built to be reviewed, not just merged

    Structured body: what changed, which success criteria it addresses, the actual audit output, and — the section reviewers come to rely on — what I was unsure about: “nested accordions have no design contract for trait propagation; left unchanged.” Plus what it deliberately did not touch, and a link to the full trajectory.

  8. AWAITING_REVIEW → ADDRESS_FEEDBACK Three comments, three different classifications

    The webhook resumes the task from its handoff record. The agent classifies each thread: one change requested (applied, gates re-run), one nit (applied), one out of scope — it files a follow-up ticket and says so in the thread rather than silently widening the diff. Scope expansion during review is a hard stop.

  9. MERGED The run becomes training data

    Trajectory, verdict, cost, and review-round count are written to the log. The reviewer's correction on the out-of-scope call becomes a playbook rule and eval case #63, so the next run doesn't relitigate it.

Schema

The two objects you'll maintain forever

A TaskSpec is one unit of work, created by intake and never mutated by the agent. A recipe is the versioned policy for a class of work — this is the artefact your team actually iterates on, and it belongs in the repo it operates on, under review, like any other code.

Policy

Autonomy is earned per recipe, capped per risk

Two independent dials. A recipe earns autonomy by demonstrated performance; the code it touches caps how far that autonomy can go, regardless of performance.

Autonomy tierWhat the agent may doPromotion evidence required
T0 · suggest-onlyComments and analysis. No branch, no diff.—
T1 · plan-approvalBranch and PR, but only after a human approves the plan.≥ 70% of its comments accepted across 30 MRs at T0.
T2 · autonomous PRBranch and PR with no plan gate. Humans still merge.Median ≤ 1.5 review rounds across 25 PRs at T1.
T3 · auto-merge on greenMerges itself when every gate passes.Only for recipes with a total oracle — dependency bumps, codemods, generated code. Never for R1.
Risk tierCode it coversAutonomy ceiling
R1Auth, payments, data migrations, cryptography, anything touching PIIT0 — permanently
R2Shared components, public API surface, build configurationT2
R3Leaf components, tests, docs, dependency bumps, codemodsT3

Ticket text and PR comments are untrusted input

Both flow straight into the prompt and both are writable by anyone with a Jira or repo account. Treat them as data, never as instructions: text arriving from a ticket or a comment must never be able to widen the tool ACL, change the path allowlist, raise the budget, or trigger a merge. Those are orchestrator decisions, made before the agent starts and immutable for the life of the run.

Build order

What to have working, and when

Weeks 1–3

Make the repo agent-runnable

One-command bootstrap, hermetic tests, targeted test selection, structured failure output from every scanner. Encode the a11y definition as an executable suite. Mine past PRs into a golden eval set.

Done when a new engineer — and a container — can go from clone to green suite in one command, and you have ~100 labelled cases.

Weeks 4–6

Ship mr-review, read-only

Two or three repos, T0 autonomy, no write access anywhere. Build the trajectory viewer alongside it — you will need it far more than you expect.

Done when you can state the comment-acceptance rate from real data, and reviewers ask for the bot on more repos.

Weeks 7–10

Durable orchestrator + sandbox

The state machine, the runner, the gate ladder, and component-a11y-prep at T1. This is where the full build → test → PR lifecycle actually lands, on the recipe with the strongest oracle.

Done when a Jira label produces a green, reviewable PR with no human touching a keyboard in between.

Weeks 11–13

Close the review loop

Comment webhook, handoff records, feedback classification. Then intake-fix — gated behind an intake quality check that bounces underspecified tickets back to their author.

Done when a reviewer's comment is addressed without anyone re-running the agent by hand.

The five numbers to publish

Autonomous merge rate
Share of agent PRs merged with no human commits pushed on top.
Review rounds per PR
Median. The single best proxy for whether the agent understood the task.
Human edit distance
Lines a reviewer changed on the agent's diff before merging.
Escape rate
Defects in production traced back to agent-authored PRs, against your baseline.
Cost per merged PR
Fully loaded — including abandoned runs, which is the point.

The hard part

It won't be the agent

The binding constraint is task specification quality. Most tickets in most backlogs do not contain enough information for a competent human to work unsupervised either — they rely on the tribal context an assignee already has. An agent has none of it, and will confidently produce something plausible and wrong.

So budget real effort for the intake gate: the part of the system that detects an underspecified request and asks a question instead of guessing. It is unglamorous, it is where the CLARIFY state in Figure 2 earns its place, and it will do more for your merge rate than any model upgrade.
